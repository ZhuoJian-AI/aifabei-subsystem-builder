# 原生聚合与扩展

本规则用于区分“新建模块系统”“给现有系统增加子模块”和“接入老系统”。目标不是把企业系统搬进灼见服务器，而是让远端业务系统在员工看来成为灼见企业大模块的一部分。

## 两种边界

```text
爱法贝企业大模块（灼见逻辑聚合）
├─ 模块系统 A（applicationSlug；本地 Git/域名/数据库/发布边界，可不直接展示给员工）
│  ├─ 子模块 A1（moduleKey；授权和导航边界）
│  │  ├─ 页面 pageKey
│  │  └─ Action actionKey
│  └─ 子模块 A2
└─ 模块系统 B
   └─ 子模块 B1
```

`applicationSlug` 回答“代码和服务如何部署”；`moduleKey/pageKey` 回答“员工看到什么、能做什么”。不要因为出现一个新的业务页面、参与部门或权限组合就创建新的 `applicationSlug`。

## 决策规则

增加 `moduleKey`，当且仅当新业务可以沿用现有系统的域名、本地 Git、数据库责任方和发布周期。典型请求包括“在样品系统里增加质量结论”“再加一个供应商评审子模块”。执行时：

1. 读取现有项目和 `subsystem.json`/Manifest，记录 `applicationSlug`、已有 `moduleKey/pageKey/actionKey`。
2. 沿用本地 Git 项目、域名、Docker 容器标识、接入密钥、数据库和数据目录；以数据库迁移增加新表/字段，不覆盖旧数据。
3. 在 `modules[]` 追加稳定且不重复的 `moduleKey`；为它声明 owner/协作部门责任、`accessRoles` 角色建议、页面、Action 和事件。
4. 页面路由必须与旧页面共存。更新后旧、新模块的健康检查、SSO、查询 Action 和既有数据都要通过。
5. 发布后让灼见重新同步同一个应用的 Manifest。新增模块、角色建议、页面和 Action 保持待授权，由平台管理员或企业管理员映射到平台角色并确认；业务 AI 不自行授权，部门责任变化也不自动扩权。

新建 `applicationSlug`，仅当至少一项成立：需要独立域名或故障隔离；数据归属/合规要求独立数据库；需要独立本地 Git 和发布回滚；现有系统技术边界无法安全承载。新系统仍聚合到同一企业大模块，不等于员工端再出现一个粗粒度外链。

## 原生体验与老系统 iframe

老系统兼容模式可以嵌入整个既有网站并允许二次登录；没有 Manifest、页面上下文和统一 Action 时，只能标记为兼容接入。

灼见原生模块即使使用 iframe/微前端作为运行隔离，也必须满足：

- 灼见侧按企业、`moduleKey`、`pageKey` 生成导航和授权，不把域名当作员工唯一入口。
- 用户只登录灼见一次；模块使用一次性 SSO ticket，不出现自己的登录页。
- 灼见打开 Manifest 中被授权的具体 `routePattern`，远端页面不重复渲染企业导航和系统外壳。
- 当前 `moduleKey/pageKey`、筛选和选中实体通过安全 Bridge 告知灼见；AI 只获得该页面允许的 Action。
- 页面按钮和 AI 调用同一业务服务函数；数据留在企业模块数据库，跨系统通过 Action 和事件流转。

因此 iframe 是可替换的容器技术，不是原生或老系统的判断标准。判断标准是是否具备 SSO、Manifest、页面级授权、上下文、Action 和事件契约。

## 管理员与业务 AI 交接

管理员给业务 AI 的环境档案只提供目标企业、现有 `applicationSlug`、项目地址、域名、部署目标和 Secret 引用，不包含另一系统的信息。业务 AI 完成后输出 Manifest 差异：新增/保留/停用的子模块、页面、Action、事件和数据库迁移。

管理员黑盒验收：

1. 同一入口的 Manifest 同时包含旧、新 `moduleKey`。
2. 未授权用户看不到新增导航，伪造 `moduleKey/pageKey` 返回 403。
3. 授权用户从灼见直接进入具体页面且不二次登录。
4. AI 能读取当前页面上下文，通过统一 Action 完成获授权 CRUD；高风险操作仍需确认。
5. 旧模块、旧数据和旧 Action 回归测试通过。

如果协议和后端满足但员工端仍只显示 `applicationName` 一级入口，应记录为灼见聚合前端缺口，不得把远端系统复制到灼见服务器或再创建一个入口掩盖问题。
